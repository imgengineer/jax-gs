# Fixed-model viser viewer — 2026-10-02

The viewer precompiles 640×360, 640×480, 1280×720 and 1920×1080 with JAX/CuTe.
Camera position, orientation, field of view and viewport aspect remain dynamic.
Model arrays and cluster bounds stay on the GPU as arguments to the compiled
function; changing cameras does not embed new constants or compile new shapes.
Each tested renderer retained exactly four JIT cache entries.

[Raw samples, source snapshots and validation](viewer_20261002.json) include
model SHA-256 hashes, every timing sample, p95 latency and GPU observations.
The models and browser captures are local outputs and are not bundled.

## Measurement scope

- RTX 5090, driver 615.71.09, Ryzen 9 9950X3D, Python 3.12.13, JAX 0.11.2,
  viser 1.1.1 and CUTLASS DSL 4.8.0.
- Full SH3, 8×16 raster tiles, 8,000,000 visibility pairs and JPEG quality 90.
- Eight camera positions shift horizontally by up to 1% of the initial
  view's look-at distance. Eager and JIT paths receive identical camera inputs.
  Their timing order alternates across resolutions. All image presets preserve
  the same 16:9 viewing rays, including the 640×480 texture.
- Timings are synchronized host-call latency in milliseconds. The first three timing
  columns include rendering and uint8 conversion. The last includes GPU
  readback and viser's JPEG encoder. None includes network delivery, browser
  decoding/display or initialization. They are not browser FPS measurements.
- Every pose is warmed before measurement. The first-call warmup totals were
  6.87 s for bicycle and
  7.90 s for the native LiteGS model.
  Local CuTe caches already existed, so these are process warmup times rather
  than clean-install compilation times.
- No other GPU compute PID was observed: 193
  samples for bicycle and 376 for the native model,
  sampled approximately every 0.5 s. Regression tests and browser sessions
  were stopped for the timed runs.

The eager path repeatedly executes Python/JAX/CuTe launch preparation; JIT
removes that repeated host work. The large eager/JIT ratio does not describe
an equivalent change in kernel arithmetic or training performance. Training
and the existing documented compiled renderer already use JIT.

## Bicycle, 975,104 Gaussians

This project's default 10k schedule, with `images_4` and evaluation enabled,
produced 9,971 updates from 169 training views. The initial viewer camera uses
the first registered COLMAP pose and vertical field of view. There are 50
samples per measurement column and resolution.

| Resolution | Eager call | JIT, moving | JIT, fixed | Render + readback + JPEG |
| --- | ---: | ---: | ---: | ---: |
| 640x360 | 391.298 | 0.744 | 0.734 | 1.486 |
| 640x480 | 394.032 | 0.750 | 0.738 | 1.622 |
| 1280x720 | 394.167 | 0.725 | 0.718 | 2.799 |
| 1920x1080 | 395.904 | 0.832 | 0.830 | 5.097 |

At 720p, JIT p95 was 0.746 ms.
Readback and JPEG encoding dominate the additional frame-delivery preparation
cost at the larger resolutions.

## Native LiteGS model, 982,912 Gaussians

An existing XiaoChe0918 PLY uses the viewer's automatic model-bounds camera.
There are 100 samples per measurement column and resolution. It is a separate
scene/view workload, not a native LiteGS renderer timing comparison.

| Resolution | Eager call | JIT, moving | JIT, fixed | Render + readback + JPEG |
| --- | ---: | ---: | ---: | ---: |
| 640x360 | 435.196 | 5.209 | 5.271 | 6.067 |
| 640x480 | 425.266 | 4.044 | 4.081 | 5.021 |
| 1280x720 | 438.968 | 2.326 | 2.629 | 4.527 |

Resolution alone does not predict latency: projected coverage, Gaussian/tile
pairs and raster workload distribution also vary. These results cover two
local viewing paths on one GPU, not a general scene benchmark.

## Image agreement and browser checks

The native-model comparison was pixel-exact on all eight warmup poses at every
resolution. Bicycle comparisons differed by at most one uint8 level: at most
7 of 2,764,800 color channels per 720p pose and 16 of 6,220,800 per 1080p pose.
A separate eight-pose 720p float comparison found a maximum absolute difference
of 0.00048828125 in the packed renderer. The benchmark retains mismatch counts
and enforces a maximum difference of one uint8 level; it does not claim
bitwise identity for arbitrary scenes.

A real headless Chromium session displayed the bicycle model, dragged the
camera, switched through all four resolutions, zoomed, reset the camera and
resized the viewport. JPEG dimensions followed the resolution control; viewport
resizing preserved the selected texture size. No JavaScript errors occurred.
The test browser used software WebGL, so its timings are not a browser FPS
measurement. A separate real WebSocket regression covers connection lifecycle,
camera updates, resolution changes, reset messages and visibility overflow.

The full GPU regression passed **422 tests in 617.85 s**, with **99.77% Python
line and branch coverage** (2,234 statements, 322 branches). GPU DSL bodies
remain excluded from Python coverage. Ruff, offline locked dependency sync,
wheel contents and the installed CLI also passed.

## Reproduce

```bash
uv run jaxgs-view output/bicycle.ply \
  --scene /path/to/bicycle --images images_4

XLA_PYTHON_CLIENT_PREALLOCATE=false uv run python benchmarks/viewer.py \
  output/bicycle.ply --scene /path/to/bicycle --images images_4 \
  --steps 50 --output output/viewer-benchmark.json

XLA_PYTHON_CLIENT_PREALLOCATE=false uv run pytest -q \
  --cov=jaxgs --cov-report=term-missing
```

Open http://127.0.0.1:8080 after warmup. See the
[README](../../README.md#web-viewer) for CLI options.
